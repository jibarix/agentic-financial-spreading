# Where the code decides: a rules inventory

This document lists the rules inventoried in sections 4 to 12: places where the code itself decides something
during a spreading job started from the UI with its default settings. "Decides" means that code accepts, refuses,
blocks, flags, routes, chooses, sets a line's state, sets a default, enforces a limit, or overrides a model's
answer. Code that only reads, computes, records or formats is left out, except for a few display rules that say
what a person sees. Everything else in a job is judged by a model: where each printed line belongs, which pieces
make it up, and whether the filing tells. The inventory is not exhaustive. Section 13 names decisions that are
known to exist and are not inventoried here, and the parts of listed rules that were not traced.

Each entry was traced in the current code from the job's entry point to the code in question (upstream), and from
its result to the final outcome: the statement's verdict, the workbook or the job record (downstream). Where one of
the records reviewed (section 2.4) shows the path, it was checked as well.

**How to read an entry.** Each row of the tables below gives:
- **ID and title.** A short label such as B12, used only for cross-references in this document, and a plain title.
- **Kind.** One of the kinds in section 2.3.
- **Where.** The file and lines in this repository (`file:line`), with the function name where it helps.
- **What the code decides.** The rule, in plain words.
- **Switch.** The setting or command-line flag that turns the rule on or off, or "none" when it always applies.
- **Downstream.** What later steps do with the result, up to the verdict, the workbook or the record. A result
  that later code overrides, ignores or uses only as a hint is said to be so.
- **Evidence.** One of the three labels in section 2.4, given per branch where the branches differ.

Line numbers refer to the code as published with this document. The tests are not covered.

## 1. Scope: the default job

The UI loads the default settings (`data/manifests/full_pipeline_monarch_v31.json`), picked at
`ui/setup_status.py:21`. The file's name is only a name; section 12 says what its `filing` key does. In the
default settings:

- **Template:** `rulebook/draft/A1_template_v16.json`. Its outcome checks name three sections, BS.TOT (the
  balance sheet's totals section), IS.OP (the income statement's operating section) and IS.NI (the income
  statement's net income section), and the report checks R1, R3, R5 and R6 (B30).
- **Spread arguments:** `--no-a2 --cap 8 --answer-cap 600 --row-seed 20261029 --combined-fixes --statements-only`.
  `--no-a2` is a compatibility flag that changes nothing (`spreading/spread.py:3109`); the retired `--a2` is
  refused (`:3179-3180`). Not every printed line reaches the analyst: statement controls, context lines (2.1),
  unsigned queued lines (B25) and the two zero-call exits of the queue (J4) are settled by code.
- **Prompts:** placement prompt `prompts/c4_place_v29.txt` (`--statements-only` selects it over the combined
  prompt, `spreading/spread.py:2051`, `:3163-3164`, `:3170-3174`); organizer prompt `prompts/organizer_v5.txt`

- **Named totals:** on (`named_totals` true). The corrections step runs before the spreads (L2).
- **Repair tree:** off (`tree.on` false, `tree.max_sections` 4). The UI forces it off (B61).
- **Limits:** company limits of 400 requests, 4.8M tokens and 3600 s, with the tiebreaker held to 80 requests and

- **Context size:** the line-up sets its own context window of 32,768 tokens, which replaces each statement's

**The line-up.** The UI offers one line-up, the default line-up: Claude Haiku 5.5 analyst and organizer, GPT-6

## 2. Terms

### 2.1 Statements, sections and lines

- **Statements:** IS (income statement), BS (balance sheet), CF (cash flow statement).
- **Sections and rows:** the template divides each statement into sections (BS.CA, IS.OP, CF.MEMO and so on), and
  each section into rows. A **spread section** has rows that add to a section total. A **memo section** has rows
  that tie to no total. In this template the cash flow statement offers no spread row; it has one memo row,
  CF.MEMO.DA (depreciation and amortization).
- **Named sections:** the three sections the template's outcome checks name: BS.TOT, the balance sheet's totals
  section; IS.OP, the income statement's operating section; IS.NI, the income statement's net income section.
  Other section IDs appear in examples, such as BS.NCL (the balance sheet's noncurrent liabilities).
- **Routed line:** a printed line with an amount whose section is set by the organizer's final sort. Code's
  structure read (J1) proposes a section, and the organizer may override it. The analyst places a routed line in a
  row of its section.
- **Queued line:** a printed line with an amount that has no section yet, an organizer blank included. It is
  settled across the statement (J4, P1, P5).
- **Context line:** a line the organizer sees but that is never placed: a heading, a statement control, an
  excluded cash flow balance (S1), a repeated occurrence of a concept, or a printed subtotal whose printed parts
  are verified to add up to it (A12).
- **Claim:** a placed amount on a row: a whole line, or a piece of one.
- **Control:** a section total, filed or reconstructed, that a section's rows are checked against.

### 2.2 Roles and steps

- **Organizer:** a model that sorts each printed line into a section, or answers "none of these sections" or
  "can't tell", citing printed text.
- **Analyst:** the model that places each line in a row, with a capped tool loop.
- **Checker:** a second model that places the same line blind, without the analyst's answer.
- **Second look:** one retry by the analyst on a disputed line, shown both answers (P3).
- **Tiebreaker:** a third model that re-solves a still-disputed line blind; code counts the vote (P2).
- **Named totals:** a model names the printed line behind each total the template needs. It is asked about every
  needed total. Where the company's tag is printed on the statement, the answer is only recorded (J2). Where it is
  not, the named line can be retagged after code's gates (B45, P4, B12).
- **Steps** (from `spreading/spread.py`): C1 period; C2 reading printed lines and routing them; C3 controls and
  signs; C4 the analyst's tool loop; C4b ownership conflicts on queued lines; C5 rows and the claim registry; C6
  checks; C7 the repair tree (off), whose name also labels the indirect-variant setup refusal; C8 the blind checker;
  C9 the verdict; C10 the record. An exception is labelled by the step that raised it.
- **R1 to R6, the report checks** of the template:
  - **R1:** the total assets row against the total liabilities and capital row.
  - **R2:** filed Assets against filed LiabilitiesAndStockholdersEquity (a check of the filing, not the spread).
  - **R3:** the cash and equivalents row against filed CashAndCashEquivalentsAtCarryingValue, reading Cash when
    that concept is not in the filing.
  - **R4:** the parent equity, preferred and noncontrolling interest rows, summed, against filed
    StockholdersEquityIncludingPortionAttributableToNoncontrollingInterest, reading StockholdersEquity when that
    concept is not in the filing.
  - **R5:** the total assets row against filed Assets.
  - **R6:** the revenue row against filed Revenues, reading either revenue-from-contracts-with-customers concept
    when Revenues is not in the filing.
- **R7, the cross-dimension overlap policy** (`spreading/steps.py:480-486`): not a report check. Under R7, two
  concepts related by a calculation, in contexts with different dimensions, read as an "unknown" overlap rather
  than an overlap (B47). It is on only with `--root-cause-fixes`, which the default job does not pass.
- **Run variant:** whether a spread ran with `--root-cause-fixes` or without it. The repair commit reads the
  variant from the run's own record and refuses a version whose variant cannot be read or is not the job's own
  (B4, B39). The code's name for it is "arm".
- **Repair invariants I1, I4 and I5** (`spreading/repair.py:54-58`), among those the repair tree's gate tests
  (B38): I1, source amounts are unchanged and read by fact ID; I4, each filed amount is owned at most once; I5, a
  split adds up to its parent and passes the shared split checks.
- **Outcomes of a statement:** **complete** (no counted check fails and no counted exception stands),
  **qualified** (every counted check passes and a counted exception stands), **blocked** (a counted check fails,
  whatever exceptions stand), **not run** (refused or failed before an outcome).

### 2.3 Kinds

- **Highlighted decision:** code decides a line's place, status or outcome without a model or against one.
- **Structure read:** code reads the filing's tags, headings, calculation links, member rows or printed page.
- **Check that blocks or flags:** a check whose failure refuses, blocks, qualifies or records.
- **Configured mapping or setting:** a stored list or wiring in the template or settings.
- **Scope rule:** what is in or out of the job.
- **Settlement policy:** which answer stands when models differ, or which line may serve which total.
- **Refusal threshold:** a numeric cut-off that refuses.
- **Default value:** a value code supplies when the filing gives none.
- **Hard limit:** a cap on steps, requests, tokens, time, dollars or size.
- **Display only:** a rule that decides what a person sees, with no effect on any outcome.

### 2.4 Evidence labels

The records reviewed are of two sets. **The current record** is one default job made with the code published here
and the workbook record made from it. **The earlier records** are four job records made with earlier versions of
the code and one workbook record made with an earlier version of the workbook code. The earlier versions differ
from the published code in places; an entry cites an earlier record only where a comparison of the files shows its
path unchanged, and says so where only part of the path is unchanged.

- **Seen in the current record:** the path appears in the current record.
- **Seen in an earlier record; path unchanged:** the path appears in an earlier record, and the code on this path
  is the same as the published code.
- **Traced in source; not observed in the records reviewed:** read in the code; none of the records reviewed shows
  the path. Other records, not reviewed, may.

## 3. Summary in plain words

Most of what code decides is reading the filing (tags, headings, calculation links, member rows and the printed
page) and running checks that block or flag. On top of that:

- **Four highlighted decisions on lines** (section 4). Verified subtotals are never placed (J1). The company's own
  printed tag wins over the named-totals model (J2). When both models put a queued line outside every total but
  the filing's calculation puts it inside one, code marks it unresolved, which blocks the statement (J3). On the
  cash flow statement, a line the organizer called "none of these sections" is recorded outside without asking a
  placement model (J4).
- **Three workbook decisions** (section 8): each line's status (B41), which lines count in the coverage figures
  (B42), and whether each printed total is compared by a check (W1).
- **Named policies** (section 5): stored totals, fallback concepts and title words in the template; the row seed;
  which cash flow lines are out of scope; which model's answer stands when they differ; the memo-only agreement
  gate; one refusal threshold for the organizer; two default signs.
- **Hard limits** on every loop and every request (sections 9 and 10).

No code branches on a particular company (section 12).
